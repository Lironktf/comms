# x402 integration

Both paths are built on the official x402 v2 TypeScript packages (`@x402/core`, `@x402/evm`,
`@x402/express`, `@x402/fetch`, pinned at 2.19.0 like the rest of Grayr) and exercised end to end
in `client/test/x402.e2e.test.ts`.

## Path A: the `shielded` scheme

| side | class (client/src/x402/index.ts) | implements |
|---|---|---|
| merchant (resource server) | `ShieldedServerScheme` | `SchemeNetworkServer` (`parsePrice`, `enhancePaymentRequirements`); also the 2.28 fields `defaultAssetTransferMethod` / `paymentFlows` |
| facilitator (natural home: Grayr) | `ShieldedFacilitatorScheme` | `SchemeNetworkFacilitator` (`getExtra`, `getSigners`, `verify`, `settle`) |
| agent | `ShieldedClientScheme` | `SchemeNetworkClient` (`createPaymentPayload`) |
| glue | `localFacilitatorClient(x402Facilitator)` | in-process `FacilitatorClient` |

### Wire format

The 402 response (`PAYMENT-REQUIRED` header, base64 JSON) looks like:

```jsonc
{"x402Version":2,"accepts":[{
  "scheme":"shielded","network":"eip155:31337","asset":"<USDC>","amount":"250000","payTo":"<merchant>",
  "maxTimeoutSeconds":300,
  "extra":{"pool":"<ShieldedPool>","feeRecipient":"<relayer>","fee":"10000","bundleUploadUrl":"https://facilitator/v1/bundles"}
}]}
```

The client's `PAYMENT-SIGNATURE` header (base64 JSON PaymentPayload) has a `payload` that is
either `{bundleRef: "<sha256 hex>"}` or `{bundle: <wire bundle>}`.

**Why by reference.** An UltraHonk proof is ~8 KB. Hex inside JSON, then base64, puts the header
at about 25 KB. Node's default header limit is 16 KB total, and the e2e test hit HTTP 431. So the
client first POSTs the bundle to the facilitator's `bundleUploadUrl` and sends only its content id:

- The facilitator only reads its own store and never fetches a client-supplied URL, so there is no SSRF.
- The id is the sha256 of the bundle, so the bundle can't be swapped.

Inline bundles still work for transports without header limits.

### Facilitator `verify`

1. Check scheme, network and pool.
2. Check the bundle is a payment (`transact` or `policyPay`) whose **recipient == payTo**,
   **amount == required amount** and **token == asset**.
3. Check the requestId is non-zero and bound, and the deadline is within `maxTimeoutSeconds` + slack.
4. Run the relayer checks:
   - the fee is at least the relayer's minimum and paid to the relayer;
   - an `eth_call` simulation of the pool call, which verifies the proof, roots, nullifiers,
     association set and vendor root on-chain, without spending gas.

`settle` submits the pool call: `transact`, or `payWithPolicy` for policy agents. The merchant
receives USDC in that transaction. Batching facilitators can queue (`Relayer` with `batch`).

### Agent code

```ts
const pay = wrapFetchWithPayment(fetch, new x402Client().register("eip155:84532",
  new ShieldedClientScheme({wallet: agentWallet, maxFee: 20_000n})));
const res = await pay("https://api.example/forecast");   // 402 -> prove -> pay -> 200
```

With an `AgentWallet`, the same call produces a `policy_pay` proof, so the agent's spending policy
is enforced inside the proof.

## Path B: zero merchant changes (`exact`, payer = pool)

`PoolExactClientScheme` registers as scheme **`exact`**. On a 402 it:

1. Proves `authorizeTransfer` and relays it, so the pool registers ONE EIP-3009 digest.
2. Returns a completely standard `exact` payload:
   `{signature: POOL_SIGNATURE, authorization: {from: pool, to, value, validAfter, validBefore, nonce}}`.

The merchant's stock `@x402/evm` server and facilitator then settle as usual. Details,
verification and caveats are in path-b.md.

## Interplay with Grayr's ACTP decision tokens

Grayr's existing x402 enforcement (`backend/src/rails/x402.ts`) is a settle-time guard: the
facilitator refuses to settle without an ACTP decision token bound to the payment.

- The two compose. A Grayr facilitator can require both a valid shielded proof and an ACTP token.
- **But an ACTP decision names the agent principal**, so it reveals the payer to Grayr's backend.
- **The in-proof policy (`policy_pay`)** is the private alternative: verified merchant, caps and
  budget are enforced without anyone, including Grayr, learning who the agent is.
- The trade-off is expressiveness. ACTP's policy language (risk scores, contract terms, human
  approval) is far richer than what is efficient in a circuit.
